# 合并

合并什么时候跑什么、`compare` 怎么读。多个代理同时工作时的约定在[给代理的约定](agents.md)。命令见 [WORKFLOW](WORKFLOW.md)。

## 合并顺序

**模块之间有数据耦合：** 形体改了，头部、贴合、绑定的指标基线都会跟着动，这种变化不算那些模块的回归。所以：

- 一次只合并一个分支。合并前用 `uv run sotaigen-dev compare --against <主仓库 build>` 把关；有退化的要么在报告里说明并得到认可，要么不合并。合并后主仓库的 `build/` 就成为新的“改前”。
- 交付前先合并最新 `main`，在它上面重跑合并层测试（`uv run sotaigen-dev test-merge`）和 `compare`，报告的“改前”以合并后的 `main` 为准，并写明提交号。
- 上游变化让别处的指标变差时，先报告，不要顺手改别处去吸收。

**合并时跑什么，同一份代码树不跑第二遍：**

| 合入的内容 | 跑什么 |
|---|---|
| 只有文档 | 只跑文档检查 `uv run sotaigen-dev lint --docs-only` |
| 不进指纹的工具（`compare`、`review`、`render`、诊断脚本） | ruff 和文档检查及相关测试文件（点名文件时慢用例照跑） |
| 导出和运行时（`export`、`web/`） | 再加 `pnpm run runtime-check`；改到页面再加 `pnpm run web-check` |
| `sotaigen/`、`data/`、`template/`，已在这棵树上验证过 | `git rev-parse HEAD^{tree}` 相同就不重跑合并层测试（`uv run sotaigen-dev test-merge`），只在主仓库运行流水线构建更新基线 |
| 同上，但合并后代码树变了 | ruff 和文档检查、流水线构建、合并层测试（`uv run sotaigen-dev test-merge`）、`compare`，改到导出再加 `pnpm run runtime-check`。流水线构建在前，合并层测试（`uv run sotaigen-dev test-merge`）直接用它的结果。两者都不烘焙接触表，改到接触代码时另跑完整层测试（`uv run sotaigen-dev test-full`） |

改到构建输入的合并完成后，按上表在主仓库运行流水线构建更新基线：贴合和绑定输入变化会让旧结果失效，别的分支正把它当“改前”。纯文档变动按文档检查一行处理。

**`compare` 怎么读：** 比较 `wrap.json`、`poses.json`、`joints.json`，并按哈希比较 `wrapped.npy`、`rest.npy`、`skeleton.json`、`weights.npz`，默认只列有变化的。

| 退出码 | 含义 |
|---|---|
| 0 | 没有退化，软指标和几何的变化照常列出 |
| 1 | 退化：`flippedFaces`、`crossedMidline`、`collapsedFaces`、`legsPastMidline` 变多，要先解释清楚 |
| 2 | 无法比较：缺文件、只有一边有的身体、当前结果过期。增删身体时显式列出两边都有的身体 |

只有一边有的姿势会列出来，但不算退化，退出码仍是 0，因为姿势可以增删。合并时要看列表，确认姿势是有意删除的。

塌陷面变多时，它会提示用 `motion folds` 看这些面是否在卡片预期的折痕里。在折痕里也仍是退化，仍要用户认可。

它只查这四个硬指标。`selfIntersections` 只列出，因为接触是合法的。塌陷面数和观感也不总是一致，比如权重拟合让数字变多、图上变好，所以退化要结合看图判断，并让用户认可。

**变化在哪里：`displacement`。** `compare` 的哈希只说网格变了，不说变在哪里。`uv run sotaigen-dev displacement --against <改前 build>` 按模板的顶点顺序逐点相减，所以同一编号就是同一位置，结果是精确的，不用匹配也不用采样。它只读两边的 `poses/<姿势>.obj`，不构建，也不碰接触表。

- **怎么读：** 每个顶点的位移拆成两部分：沿改前法线的部分（正值是向外，那里变饱满了），和沿表面的滑动（着色图上看不出来）。
- **`summary.txt`：** 每个姿势一行，写最大位移在哪一段、p95，以及位移主要集中在哪些部位；完全没变的姿势按身体合成一行。先看这个文件。
- **`displacement.json`：** 每个身体、每个姿势的数据：全身，模板的每个区域和分段（四肢分左右），以及相距 40 mm 以上的最大几处位移，含顶点号、位置、向外量和滑动量。`share` 是该组占全身位移总量的比例，用来判断“改动是否只落在该改的地方”。
- **热图：** 两行，向外量（蓝内红外）和位移大小，正交投影、按 `--mm-per-px` 出图，和 `review` 一样可以直接量长度。最大位移按 JSON 的顺序编号。位移集中在一处时，下面再加一组 1 号位置的近景，从身体上切出来，不会被别处挡住。不传 `--scale` 时每张图按自己的最大值取色标，跨图比较要传同一个 `--scale`。
- **它不判断好坏：** 位移只说明哪里变了、变了多少，是否认可仍要看图，并由用户决定。

多个代理同时工作时的约定见[给代理的约定](agents.md)。
